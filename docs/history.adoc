= pl-shexec: history
:toc:

== Abstract

pl-shexec began in 2022 as a thin ChRIS wrapper around pfdo_run 3, carrying pfdo_run's own 1.x tag grammar, a pftel telemetry flag, and the dependencies of its day. Version 2.0, in October 2026, is the same idea on the rebuilt stack: pfdo_run 4 on hostlib and pftag 3, pflog 2 for the run's span, chris_plugin's decorator, a package of three modules, a workflow that tests before it builds, and an exit status that means what it says.

== 2022 to 2023: a wrapper on pfdo_run 3

The first pl-shexec was one file, `shexec.py`, from the python-chrisapp-template: a `@chris_plugin` main that copied the parsed namespace into pfdo_run's dictionary-of-options constructor, renamed `inputdir` to `inputDir` with a comment about camel-case annoyances, and called `run`. The parser was pfdo_run's `parserDS` with one flag added, `--pftelDB`, and `main` wore pflog's `tel_logTime` decorator, which posted the seconds `main` took to a pftel server when the flag was set. The manual was pfdo_run's text concatenated with the plugin's own. The command grammar was pfdo_run 3's: `%inputWorkingDir`, `%_rmext_inputWorkingFile`, and the whole of pfdo_run 3's behaviour came with it, the split-on-whitespace command, the stderr read after exit, the dropped last line.

The packaging recorded what the plugin had accumulated. `setup.py` declared one dependency, chris_plugin; `requirements.txt` pinned fourteen, among them pudb, Faker, urwid, Pygments and pftel-client, and the Dockerfile installed them twice and the package twice. The test was the template's, counting words in a text file, and the workflow's test job was set to `if: False`. The image, on `python:3.11.0-slim-bullseye`, installed neovim and telnet beside the tools the template could use. The last commit before 2.0, in 2023, added the DCMTK tools. `main` returned 0 whatever pfdo_run reported, so a plugin instance whose every job failed was marked successful in ChRIS.

== 2026: the same plugin on the rebuilt stack

The pf* revitalization of October 2026 rebuilt pftree, pfdo, pftag and pfdo_run in order, created hostlib for running a process, and rebuilt pflog for timing a call, each repository on its own branch and pull request and each published before the next began; pl-shexec was the first plugin on the result, and the reason the chain had been walked, since pl-freesurfer was to be built on its design.

Three decisions were taken for the plugin itself. The telemetry flag went, with the discussion recorded in pflog's history: the run's timing stays, as a span on standard error where CUBE and any collector already look, and the transport to a server is no longer the plugin's business. The parser became pfdo_run's with no additions, which required pfdo_run 4.1 to let `parser_build` take the command's name and version so the plugin could answer `--help` and `--version` as itself; the plugin therefore has no parameters to maintain and inherits every improvement to pfdo_run's, including the `--exec` help that names the tags, added in pfdo_run 4.0.1 after the observation that nothing short of the manual had told a user the flag carried a grammar. The exit status became truthful, 0, 1 or 2 from the run's record, so ChRIS marks a failed run failed.

The shape followed the stack's: a `shexec` package with `__main__`, `shexec` and `models`, the last re-exporting every record of the layers below; `pyproject.toml` with three dependencies in place of `setup.py` and fourteen pins; twelve tests run in-process and one through `chris_plugin_info`; a workflow whose test job gates the image build; a `python:3.12-slim` image with one install; a README for someone who has never seen a pf* tool; and these three documents. One accommodation was made to chris_plugin 0.4.0: the plugin module omits the `from __future__ import annotations` the stack uses everywhere else, because the decorator inspects `main`'s annotations as objects to tell a DS plugin from an FS plugin.

Version 2.0.1 followed the first upload to cube.chrisproject.org, which CUBE refused with `documentation: This field may not be null`: `chris_plugin_info` reads the legacy `Home-page`, `Author` and `Author-email` metadata fields, which a `pyproject.toml` project table does not emit, so the description had no documentation URL and an author of `None`. A `setup.cfg` carrying those three fields beside the pyproject restores them, and the test of the description now checks both.

Version 2.0.2 rebuilt the image on pfdo 6.2.0, published two hours after the 2.0.1 image was built, and named pfdo in the plugin's own dependencies so that the image states the stack it carries rather than inheriting it through pfdo_run.

Version 2.0.3 told the other half of the story. The README had presented the plugin as the home for jobs too small to deserve a plugin of their own, which is why it sits in a pipeline, and had left out that it is the design for wrapping a command-line program as a plugin, which is why the stack was rebuilt; the README and the purpose now say both, with pl-freesurfer named as the first plugin cut from the shape.

Version 2.2.0 made pl-shexec a base as well as a plugin. The README of 2.0.3 had said that a plugin wrapping a program is pl-shexec with three changes, and the operator asked how that plugin is made, since the only answer the code gave was to copy three modules and edit them. `plugin_build` and `PluginSpec` are the answer: a downstream plugin depends on the `shexec` package and calls the factory with what differs, its name, its description for ChRIS, its flag defaults and its manual's words, and gets back its parser, its manual and its decorated main; pl-shexec's own `__main__` became the first call of the factory, and pl-freesurfer the second. The record of each job also became one line in the directory's `jobs.jsonl`, following pfdo_run 4.2, with the four files behind `--jobFiles`.

Version 2.3.0 let a plugin built on shexec decline engine flags. pl-freesurfer was the occasion: `--threads` runs that many subjects at once in one container, every `recon-all` in FreeSurfer 8 peaks near sixteen gigabytes in its SynthSeg step, and the container has one memory limit, so two subjects in a 32Gi pod is an out-of-memory kill of both, which pman then restarts on the half-written output. The decision was that such a plugin does not offer the flag at all, and that scaling across subjects is a matter of one plugin instance per subject, created by a controller plugin in the feed. `PluginSpec` gained `omit`, a tuple of destination names; the factory removes each flag from the parser, from the description ChRIS reads and from the manual's shared sections, and pins its value to the engine's default or to the spec's own default for it. argparse offers no public way to remove an argument, so the removal touches the three private structures argparse keeps a flag in, which chris_plugin itself reads and which are the same from Python 3.11 to 3.14; a misspelt name is refused when the plugin is built rather than leaving the flag silently in place.
